# [높음] 2026-09-09 잔여 WORKER_IDLE 가짜 실패 · Chrome 재기동 폭주

- **발생 일시**: 2026-09-09 (GUI 일괄 조회)
- **심각도**: 높음 (데이터 손실은 없으나 실패율·재시도·Chrome 기동 폭증)
- **관련 파일**: `services/puppeteer.py`, `src/interactive_runner.js`

---

## 1. 증상

같은 레인에서 사건 A를 끝낸 직후 사건 B를 보내면, 캡차도 오기 전에 실패 처리됐다.

```
▶ CASE 전송: {다음사건} [instance_N]
▶ 캡차·스킵 응답 대기 중
[Node] WORKER_IDLE
X 캡차 응답 없이 WORKER_IDLE
레인 워커 강제 종료
X 캡차 이미지 캡처 실패 → 웨이브에서 제외
```

한 배치에서 Chrome 기동이 20회 이상까지 늘어났다.

## 2. 영향 범위

- 실제로 조회 가능했던 사건이 “캡처 실패”로 웨이브에서 빠짐
- 같은 레인 다음 건이 연쇄 실패
- 스마트 스킵용 최근 검색 세션도 창이 새로 열릴 때마다 리셋되어 캡차 재요구와 겹침

## 3. 근본 원인

레인 워커는 사건 끝에 stdout에 `WORKER_IDLE`을 찍는다.
Python은 JSON 결과만 읽고 루프를 끝내면 **그 IDLE이 파이프에 남는다.**

다음 CASE의 캡차 대기 루프가 그 줄을 읽으면  
「캡차/스킵 없이 IDLE = 이 사건 실패」로 오판하고 `_kill_lane_worker`를 호출했다.

## 4. 왜 막지 못했나

- CASE 전송 전 stdout drain이 없었다
- “이 사건 시작 로그 이전의 IDLE”을 잔여분으로 구분하지 않았다
- IDLE만으로 레인을 죽여도 된다고 가정했다

## 5. 복구 방법

코드 수정 후 재조회. 시트 데이터 손상은 없음.

## 6. 재발 방지 코드 — 지우지 말 것

| 위치 | 가드 |
| --- | --- |
| `services/puppeteer.py` `_drain_worker_stdout` | 다음 CASE 전 잔여 IDLE/로그 폐기 |
| `services/puppeteer.py` 캡차 대기 | `사건 처리 시작` 이전 IDLE은 무시 |
| 동상 `early_fail_reason == worker_idle` | 워커가 살아 있으면 레인 kill 하지 않고 재사용 |

## 7. 교훈

1. **프로세스 간 프로토콜 메시지(IDLE/READY)는 “어느 사건에 속하는지”를 명확히 할 것.**
2. **파이프에 남은 이전 응답을 다음 요청 실패로 해석하지 말 것.**
3. **kill → 재기동은 비용이 크다.** 오판으로 kill하면 연쇄 장애가 난다.
